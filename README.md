# Jonson

The fastest way to spin up api endpoints in go:

```go
type News struct {}

type GetHeadlinesV1Params struct {
  jonson.Params
  Country string `json:"country"`
}

type GetHeadlinesV1Result struct {
  Headlines []string `json:"headlines"`
}

// GetHeadlines serves the current headlines;
// will be served on /news/get-headlines.v1
func (n *News) GetHeadlinesV1(ctx *jonson.Context,
  public *jonson.Public, _ jonson.HttpPost,
  params *GetHeadlinesV1Params,
) (*GetHeadlinesV1Result, error){
  return &GetHeadlinesV1Result{
    Headlines: []string{"Welcome simplicity!"},
  }, nil
}
```

Jonson allows you to expose API endpoints using [JSON-RPC 2.0](https://www.jsonrpc.org/specification).

You will be able to expose functions either using:

- a http endpoint per rpc
- a single http endpoint serving all calls
- websocket
- MCP (Model Context Protocol), as tools for AI agents

In order to do so, Jonson consists of:

- a server which exposes the http endpoint(s), a websocket connection and/or an MCP endpoint
- a factory which allows you to _provide_ functionality to your API endpoints
- parameter validation
- error message encryption/decryption to hide sensitive information from the client
- a code generator for typed in-process calls and providers
- test helpers (`jonsontest`) for calling your endpoints in unit tests

## Project structure

Jonson thinks in _systems_.
A system is a set of things that, as a whole, form emergence.
Systems also tend to interact with other systems. As a result, we would be talking
of a _system of systems_.

Let's assume an auth service (a system by itself).
An auth system consists of authorization and authentication (system of systems).
The ideal folder structure for a Jonson project, following the systemic approach, would
look something like this:

```txt
/<project-name>
  /cmd
    /server
      main.go
  /internal
    /systems
      /authorization
        authorization.go
      /authentication
        authentication.go 
/go.mod
```

## Remote procedure calls

When following the systemic approach, we can now start implementing our remote procedure calls.
Let's follow the example of an auth service.
The authentication endpoint might need functions like register, login and logout.
Within the autentication/authentication.go folder, we can now set up our remote procedure calls.

The remote procedure calls will be generated by the server (explained later).
In order to expose the endpoints properly, we need to follow a naming scheme:
`<MethodName>V<version>`.

A remote procedure call accepts parameters (optional) and returns a result (optional) _or_ an error.
The result is always a pointer to a struct, so that every response is a JSON object: a method returns either
`error` or `(*Result, error)`. Registering a method with any other result type (slice, map, primitive, struct value)
panics at startup, and returning `nil, nil` from a `(*Result, error)` method is an internal error.

Parameters are a pointer to a struct which **must** embed `jonson.Params`: this is how jonson tells
the parameters apart from provided types. A method may have at most one parameter struct.
Without the embedded `jonson.Params`, registering the method panics at startup ("requires unknown type").

In order to validate parameters, make the RegisterV1Params implement `jonson.ValidatedParams` interface.
By doing so, before each function call Jonson will make sure that the JonsonValidate() function will be called.
In case any errors have been added to the `v *Validator`, Jonson won't execute the given function.

```go

// Authentication is our authentication system
type Authentication struct {
}

func NewAuthentication() *Authentication {
  return &Authentication{}
}

type RegisterV1Params struct {
  jonson.Params
  Username string `json:"username"`
  Password string `json:"password"`
}

func(r *RegisterV1Params) JonsonValidate(v *jonson.Validator){
  if len(r.Username) > 20 || len(r.Username) < 5{
    v.Path("username").Code(10000).Message("insufficient length")
  }
  if len(r.Password)  < 8{
    v.Path("password").Code(10001).Message("insufficient length")
  }
}

type RegisterV1Result struct {
  Uuid string `json:"uuid"`
}

// RegisterV1 allows us to register a new account
func (a *Authentication) RegisterV1(ctx *jonson.Context, params *RegisterV1Params) (*RegisterV1Result, error) {
  if (len(params.Username) <= 5){
    return nil, jonson.ErrInvalidParams
  }
  // put your register logic here
  return &RegisterV1Result {
    Uuid: "27fd79d0-e776-41c4-809a-3d1865b4f729",
  }, nil
}

type LoginV1Params struct {
  jonson.Params
  Username string `json:"username"`
  Password string `json:"password"`
}

// LoginV1 allows an account to log in
func (a *Authentication) LoginV1(ctx *jonson.Context, params *LoginV1Params) error {
  // put your login logic here
  return nil
}

// LogoutV1 allows an account to log out
func (a *Authentication) LogoutV1(ctx *jonson.Context) error {
  // put your logout logic here
  return nil
}

```

For more complicated parameters and their validation, you can also provide validators on nested structs.
Only the top-level params embed `jonson.Params`; nested structs just implement `JonsonValidate`:

```go
type UpdateProfileV1Params struct {
  jonson.Params
  Name    string   `json:"name"`
  Address *Address `json:"address,omitempty"`
}

func(p *UpdateProfileV1Params) JonsonValidate(v *jonson.Validator){
  if len(p.Name) < 2{
    v.Path("name").Message("name insufficient")
  }
  if (p.Address != nil){
    v.Path("address").Validate(p.Address)
  }
}

type Address struct {
  Street string `json:"street"`
  Zip string `json:"zip"`
}

func(a *Address) JonsonValidate(v *jonson.Validator){
  if len(a.Street) < 2{
    v.Path("street").Message("street insufficient")
  }
  if len(a.Zip) < 2{
    v.Path("zip").Message("zip insufficient")
  }
}

```

The validator allows you to optionally set `Debug(msg string)` and `Code(code int)` to the error. In case code is not available, jonson.ErrInvalidParams' code will be used. The debug message will be encrypted and added to the error details using jonson.Secret.

Before the validation takes place, the remote procedure call's params will be unmarshaled.
The unmarshaler is configured to be strict - e.g. unknown fields will not be allowed.
In case you need to be a bit more relaxed on unknown keys, you can implement the "AllowUnknownFieldsParams" interface:

```go

type ParamsAllowingUnknownFields struct {
  jonson.Params
  Uuid string `json:"id"`
}

func (t *ParamsAllowingUnknownFields) JonsonAllowUnknownFields() {
  // do nothing
}

// make sure the interface is correctly implemented by ParamsAllowingUnknownFields
var _ jonson.AllowUnknownFieldsParams = (&ParamsAllowingUnknownFields{})
```

## Factory

Let's assume, the account wants to have access to a database or the current time.
We could provide the database to the Authentication system itself (by passing a parameter to the constructor
and keeping a reference within the Authentication struct) _or_ we start diving into the
possibility of using a factory.
A factory allows us to define certain infrastructure or functional components during startup
and _provide_ those functional components at runtime.

Going back to the "auth service" example, let's see how to add a component that provides database access and one that provides the curent time.
First, we would create a new folder `internal/infra` which will contain all files that implement our infrastructure setup.
We can now create a new `InfrastructureProvider`:

```go
type InfrastructureProvider struct {
  db *sql.Db
  newTime func() time.Time
}

func NewInfrastructureProvider(db *sql.Db, newTime func() time.Time) *InfrastructureProvider {
  return &InfrastructureProvider{
    db: db,
    newTime: newTime,
  }
}

// @generate
type DB struct {
  *sql.DB
}

func (i *InfrastructureProvider) NewDB(ctx *jonson.Context) *DB {
  return &DB{
    DB: i.db,
  }
}

// @generate
type Time struct {
  time.Time
}

func (i *InfrastructureProvider) NewTime(ctx *jonson.Context) *Time {
  return &Time{
    Time: i.newTime()
  }
}
```

In order for the providers to work, Jonson needs you to follow a specific naming scheme:
the functions providing a type need to start with the keyword "New" followed by the type
the provider instantiates, such as: `NewTime` returning *Time.

**NOTE**: your providers need to return either a pointer to a struct _or_ an interface.

You might have noticed the `// @generate` tag: these are used to mark the types that we want to be able to 'inject' and use in our systems through the use of a `Require<type>` function that will be generated by the script `jonson-generate`.
Since we tagged `Time` and `DB` in the example above, `jonson-generate` will create two functions for us:

```go
func RequireTime(ctx *jonson.Context) *Time {
  // ...
}

func RequireDB(ctx *jonson.Context) *DB {
  // ...
}
```

To register the providers in the factory, use `factory.RegisterProvider` passing the pointer to the InfrastructureProvider.
For details, check out the section "Putting it all together";

In case our provider is really simple, we can also use a single function:

```go
// @generate
type ServiceName struct {
  Name string
}

func ProvideServiceName(ctx *jonson.Context) *ServiceName {
  return &ServiceName {
    Name: "auth",
  }
}
```

To register a simple provider function, use `factory.RegisterProviderFunc` passing the function itself.
Again, for details, check out the section "Putting it all together";

Once the types are provided by the factory, you can access them in your remote procedure calls:

```go
// LoginV1 allows an account to log in
func (a *Authentication) LoginV1(ctx *jonson.Context, params *LoginV1Params) error {
  // the factory provides the database and we can now access it here in the code
  db := infra.RequireDB(ctx)

  // put your logic here
  return nil
}

```

The generated types will be instantiated _once_ per API call and then stored within the context.
In case a provider becomes invalid (e.g. we were storing a session provider and the account logged out),
we can call the `context.Invalidate` method passing the type which we need to invalidate.
The context allows us to also store new values on the fly (e.g. the user logged in and we want to provide a session)
by calling `context.StoreValue`.
**NOTE**: as a security feature, context.StoreValue will panic in case a provided value already exists;

In case you're calling a remote procedure from within a remote procedure, a new context will be created.
However, some contexts you will want to share between those calls, such as time, http request/responses and more.
For those contexts that are shareable between contexts, Jonson allows you to specify a provided type as `jonson.Shareable`:

```go
// @generate
type Time struct {
  jonson.Shareable
  time.Time
}
```

Time will now be passed between contexts.

In case you also want to make your provided values shareable across impersonation calls, mark them with `jonson.ShareableAcrossImpersonation`. Only values that are explicitly marked with `jonson.ShareableAcrossImpersonation` will
be taken across the impersonation boundaries.

Some context values want to be finalized. Jonson allows you to specify a `Finalize(errs []error) error` method
on your provided types (`jonson.Finalizeable`).
In case a finalize method is found, it will be called _after_ the remote procedure call within the context has been completed.
It receives the errors of the call so far, e.g. to roll back a transaction:

```go
// @generate
type Tx struct {
  *sql.Tx
}

func (t *Tx) Finalize(errs []error) error {
  if len(errs) > 0 {
    return t.Rollback()
  }
  return t.Commit()
}
```

The `Factory` allows for specifying a `Logger` which will be used to output certain debug logging information.
Per default a no-op-logger will be used which won't output any logging information.
In case you would like to inspect certain information from jonson, provide a logger:

```go

logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
factory := jonson.NewFactory(&jonson.FactoryOptions{
  Logger: logger,
})

```

The logger will be provided to the underlying remote procedure calls using the factory by mounting a logger provider.
Use `jonson.RequireLogger(ctx)` to get access to the logger.

The logger also allows you to log certain information by default, for example the endpoint called or the function the logger was required in.
To do so, use:

```go

logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
factory := jonson.NewFactory(&jonson.FactoryOptions{
  Logger: logger,
  LoggerOptions: (&jonson.LoggerOptions{}).WithCallerFunction().WithCallerRpcMeta(),
})

```

`WithCallerFunction` will log the current caller function using the key "function". You can provide your own key.
`WithCallerRpcMeta` will log the caller rpc meta using the key "rpcMeta". You can provide your own key.

## Method handler

The method handler parses all remote procedure calls from registered systems using reflection and exposes methods to call those remote procedure calls.
To register a system with the method handler use the function `methodHandler.RegisterSystem()`.

For each call, the method handler will also make sure that the factory's providers will be provided to the
called functions.

Besides those functions provided by the factory, the method handler will provide a few infrastructure related
providers, such as:

```go

func RequireHttpRequest(ctx *jonson.Context) *jonson.HttpRequest{}               // embeds *http.Request
func RequireHttpResponseWriter(ctx *jonson.Context) *jonson.HttpResponseWriter{} // embeds http.ResponseWriter
func RequireWSClient(ctx *jonson.Context) *jonson.WSClient{}
func RequireRpcMeta(ctx *jonson.Context) *jonson.RpcMeta{}
func RequireSecret(ctx *jonson.Context) jonson.Secret{}
func RequireLogger(ctx *jonson.Context) *slog.Logger{}
func RequireJsonHandler(ctx *jonson.Context) jonson.JsonHandler{}

```

`Require*()` calls fail hard on purpose: in case a value cannot be provided, they panic and the call is aborted.
A missing value is a wiring error, not something to handle within the method, so there is no error to check.
The panic is turned into the rpc's error response. For values which are genuinely optional, use `ctx.GetValue()`,
which returns an error instead.

The response writer only allows setting headers: the body is always the method's JSON response.
See [File downloads](#file-downloads-and-other-raw-responses) for serving files.

`RequireRpcMeta(ctx)` tells you which method is being called (`Method`, `HttpMethod`) and through which
transport (`Source`): `jonson.RpcSourceHttp` (one endpoint per method), `jonson.RpcSourceHttpRpc`
(single rpc endpoint), `jonson.RpcSourceWs`, `jonson.RpcSourceMcp` or `jonson.RpcSourceInternal`
(called by another method).

The method handler will be passed to the exposing technology during startup, such as:

- http (one endpoint per method, or a single rpc endpoint)
- websocket
- MCP
- a combination of the above

In most cases, you shouldn't need to use the method handler.
Check out "Putting it all together" to see the method handler in action.

The method handler allows for setting optional (nil) options.
You can specify the missing parameter validation level:

```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
handler := jonson.NewMethodHandler(factory, secret, &jonson.MethodHandlerOptions{
  MissingValidationLevel: jonson.MissingValidationLevelError,
})
```

By setting a different value (`MissingValidationLevelIgnore`, `MissingValidationLevelInfo`, `MissingValidationLevelWarn`, `MissingValidationLevelError`, `MissingValidationLevelFatal`), you can modify the method handler's startup behaviour.
In case of MissingValidationLevelIgnore, the validation on rpc params will be ignored.
In case of MissingValidationLevelFatal, the application will panic during startup. All other states will log to the logger
according to their level (info, warn, error).

To enforce that `JonsonValidate()` covers every param field, set `MissingFieldValidationLevel` (defaults to ignore).
At registration, jonson validates a zero value of each param struct and reports all json fields never passed to `v.Path()`.
Use the unconditional `Check` / `Skip` so fields are seen even when valid:

```go
func (p *SubmitV1Params) JonsonValidate(v *jonson.Validator) {
  v.Path("name").Check(p.Name != "", "name is required")
  v.Path("age").Code(4221).Check(p.Age >= 0, "age must be zero or greater")
  v.Path("marketing").Skip()
  v.Path("address").Validate(&p.Address)
}
```

Paths inside an `if` only count when the branch runs for the zero value.
If `JonsonValidate()` panics on a zero value (e.g. nil pointer deref), this is reported at the same level.

The remaining options:

```go
handler := jonson.NewMethodHandler(factory, secret, &jonson.MethodHandlerOptions{
  // max number of requests within a single batch (see "Batch requests"), defaults to 100
  MaxBatchSize: 50,
  // the json library used for all requests and responses, defaults to encoding/json
  JsonHandler: jonson.NewDefaultJsonHandler(),
  // change what is logged per request; params are logged encrypted with the Secret,
  // drop them in case you don't want them in your logs at all
  RpcRequestLogInfoInterceptor: func(info *jonson.RpcRequestLogInfo) *jonson.RpcRequestLogInfo {
    info.Params = "<redacted>"
    return info
  },
})
```

### Registering methods without a system

Besides `RegisterSystem`, you can register a single function under a method name of your choice.
It follows the same rules as a system's method (context first, providers, at most one params struct):

```go
methodHandler.RegisterMethod(&jonson.MethodDefinition{
  System:      "custom",
  Method:      "hello",
  Version:     1,
  HandlerFunc: func(ctx *jonson.Context, params *HelloV1Params) (*HelloV1Result, error) {
    return &HelloV1Result{Greeting: "hello " + params.Name}, nil
  },
}) // served as custom/hello.v1
```

### Calling methods in-process

`ctx.CallMethod("system/method.v1", jonson.RpcHttpMethodPost, params)` calls another method without
an http round trip. The call runs in a forked context (see "Factory": only shareable values are passed on)
with `RpcMeta.Source` set to `jonson.RpcSourceInternal`. The generated procedure calls (see "Code generation")
wrap `CallMethod` with typed params and results, so you will rarely call it directly.

## Server

The server implements the standard http.Handler interface.
You can either use the `server.ListenAndServe(":8080")` method directly _or_ alternatively
write your own server which can use the http.Handler interface provided by
the server.

`NewServer()` accepts multiple `Handler`s which can be one of:

- rpc over http (using a single endpoint): `jonson.HttpRpcHandler`
- rpc over websocket: `jonson.WebsocketHandler`
- a single http endpoint per rpc: `jonson.HttpMethodHandler`
- methods as tools for AI agents: `jonson.McpHandler`
- default http handlers which use the http.Request and http.ResponseWriter functionality: `jonson.HttpRegexpHandler`

During startup, you can decide which endpoints you want to provide.

All http handlers limit the request body to 5 MB by default. Use `WithOpts` to change the limit
(`MaxBytes <= 0` disables it):

```go
rpcHandler := jonson.NewHttpRpcHandler(methodHandler, "/rpc").WithOpts(&jonson.HttpRpcHandlerOpts{MaxBytes: 1e6})
httpHandler := jonson.NewHttpMethodHandler(methodHandler).WithOpts(&jonson.HttpMethodHandlerOpts{MaxBytes: 1e6})
```

Requests exceeding the limit fail with `ErrRequestTooLarge`.

### RPC over HTTP

The `NewHttpRpcHandler` will handle all registered remote procedure calls within a single endpoint which can be
defined by the software developer.

The exposed http endpoint will only accept POST requests.

### Batch requests

Over the single rpc endpoint and websocket, you can send multiple requests at once by sending a JSON array
(a [batch](https://www.jsonrpc.org/specification#batch)). The response is an array as well.
Requests without an `id` are notifications: they are executed, but a successful call is not answered.

```json
[
  { "jsonrpc": "2.0", "id": 1, "method": "account/get-profile.v1", "params": { "uuid": "..." } },
  { "jsonrpc": "2.0", "id": 2, "method": "account/get-settings.v1" }
]
```

A batch may contain at most `MethodHandlerOptions.MaxBatchSize` requests (default 100); larger batches are
rejected as a whole with `ErrRequestTooLarge`.

### RPC over HTTP: one endpoint per method

The `NewHttpMethodHandler` will expose each remote procedure call as its own endpoint.
By default, none of the endpoints will check for the correct http method.
In case you want to enforce the usage of GET or POST, use jonson.HttpGet and jonson.HttpPost
as parameters within your remote procedure call.
RPC over a single HTTP endpoint, websockets and MCP only use POST: a method requiring
jonson.HttpGet is rejected with `ErrServerMethodNotAllowed` there, and `McpHandler.Expose` panics on it.

```go
// LoginV1 allows an account to log in
func (a *Authentication) LoginV1(ctx *jonson.Context, _ jonson.HttpPost, params *LoginV1Params) error {
  // the factory provides the database and we can now access it here in the code
  db := infra.RequireDB(ctx)

  // put your logic here
  return nil
}
```

Now, the endpoint will only accept http calls using POST.
In case the endpoint is called using a single endpoint for rpc or websocket, the required jonson.HttpPost has no effect.

Besides a JSON body, this handler accepts params from the **query string** (e.g. for GET requests) or as an
**`application/x-www-form-urlencoded`** body. The field names are the params' `json` tags, the values are
converted to the field types, and unknown fields are rejected like for JSON (unless the params implement
`AllowUnknownFieldsParams`). Params can only come from one source: sending a body _and_ a query string fails
with `ErrInvalidParams`.

```txt
GET /news/get-headlines.v1?country=de
```

### RPC over websocket

`NewWebsocketHandler` serves all methods over a websocket connection on the given path. Each message is a
JSON-RPC request (or batch); messages of one connection are processed concurrently, so responses may arrive
in a different order than the requests: match them by `id`.

```go
wsHandler := jonson.NewWebsocketHandler(methodHandler, "/ws", jonson.NewWebsocketOptions())
```

`NewWebsocketOptions()` returns the defaults, which you can adjust:

| Option | Default | Effect |
|---|---|---|
| `Upgrader` | 1 KB read/write buffers | the gorilla websocket upgrader, e.g. to set `CheckOrigin` |
| `MaxMessageSize` | 4 MB | max size of a single incoming message |
| `PongWait` | 60s | the connection is closed if the client does not answer pings within this time |
| `PingPeriod` | 54s | interval of pings sent to the client, must be shorter than `PongWait` |
| `WriteWait` | 10s | timeout for writing a single message |
| `MaxConcurrentMessages` | 64 | max messages processed in parallel per connection; once reached, reading pauses until a slot frees up |

The server can push messages to the client: a method called over websocket can send JSON-RPC
notifications (requests without `id`) before it returns, e.g. to report progress:

```go
func (i *Import) RunV1(ctx *jonson.Context, params *RunV1Params) error {
  client := jonson.RequireWSClient(ctx)
  // client.IPAddress() and client.UserAgent() describe the connection
  for n, row := range params.Rows {
    // process row
    client.SendNotification(jonson.NewRpcNotification(ctx, "import/progress", map[string]int{"done": n + 1}))
  }
  return nil
}
```

`RequireWSClient` is only available for calls over websocket.

### File downloads (and other raw responses)

Remote procedure calls do not serve files. A remote procedure call always responds with its JSON result or
a JSON error, regardless of the transport (http, rpc over http, websocket, MCP). Methods may set headers
using `RequireHttpResponseWriter(ctx)`, e.g. to set a cookie, but writing a body or a status code is rejected
with `ErrServerMethodNotAllowed`.

To serve a file, register a plain http handler with the `HttpRegexpHandler` instead. It works with the
http.Request and http.ResponseWriter directly, and still receives providers from the factory, such as
`jonson.Private` for authorization:

```go
regexpHandler := jonson.NewHttpRegexpHandler(factory, methodHandler)

regexpHandler.RegisterRegexp(regexp.MustCompile(`^/files/([0-9a-f-]+)$`), func(
  ctx *jonson.Context,
  _ *jonson.Private, // only authorized accounts may download
  w *jonson.HttpResponseWriter,
  parts *jonson.HttpRegexpMatchedParts,
) {
  // parts.Parts[0] is the full match, parts.Parts[1] the file id
  f, err := files.Open(parts.Parts[1])
  if err != nil {
    // a jonson error is returned to the client as json
    panic(jonson.ErrInternal)
  }
  defer f.Close()

  w.Header().Set("Content-Type", "text/csv")
  w.Header().Set("Content-Disposition", `attachment; filename="export.csv"`)
  io.Copy(w, f)
}).WithRpcMethod("files/download.v1") // the method name the auth client checks in RpcMeta
```

A regexp handler is not a remote procedure call: it cannot be called by other methods, over rpc, websocket or MCP.

### MCP: methods as tools for AI agents

The [Model Context Protocol](https://modelcontextprotocol.io) is JSON-RPC 2.0 as well, so `NewMcpHandler` serves
registered methods as MCP tools. A tool call runs through the same pipeline as every other handler:
providers, auth, validation, logging and the error `Secret`. Inside the method, `RequireRpcMeta(ctx).Source`
is `jonson.RpcSourceMcp`.

Only the methods you pass to `Expose` become tools, each with a description for the model.
Pass the method value of a registered system; methods registered by name with `RegisterMethod`
can be exposed with `ExposeMethod("system/method.v1", ...)`.
Without a description, the method's doc comment is used: `jonson-generate` writes it into
`jonson.descriptions.gen.go` (as `JonsonMethodDescriptions`, see `jonson.MethodDescriber`):

```go
mcpHandler := jonson.NewMcpHandler(methodHandler, "/mcp").
  Expose(authentication.LoginV1, "Logs an account in and returns a session.").
  Expose(account.GetProfileV1) // uses the doc comment of GetProfileV1

server := jonson.NewServer(mcpHandler, rpcHandler, httpHandler)
```

To expose many methods at once, `ExposeSystem(account)` exposes all methods of a registered system and
`ExposeAll()` all endpoints registered so far. Both rely solely on the generated descriptions: they panic
on a method without doc comment, and skip methods requiring GET as well as tools that are already exposed,
so `Expose(account.GetProfileV1, "custom description").ExposeSystem(account)` keeps the custom description.

- Tool names replace `/` and `.` with `_`: `account/get-profile.v1` becomes `account_get-profile_v1`.
- The `inputSchema` of a tool is built from the params struct: `json` tags give the names, fields without
  `omitempty` or `omitzero` are required, except pointers, slices and maps (missing ones decode to nil), and a `description:"..."` tag documents a field for the model.
  Without a tag, the field's code comment is used: `jonson-generate` writes the comments of all exported
  structs into `jonson.descriptions.gen.go` (as `JonsonFieldDescriptions`, see `jonson.FieldDescriber`).
  Unknown fields are rejected unless the params implement `AllowUnknownFieldsParams`.
- A successful call returns the result as `structuredContent` and as text. The text is the result's JSON, unless the
  result implements `jonson.McpTextSummarizer`: then `JonsonMcpTextContent()` gives a short summary for the model
  instead, so the data is not sent twice:

  ```go
  func (r *GetProfileV1Result) JonsonMcpTextContent() string {
    return "Profile of " + r.Name
  }
  ```

  To find tools without a summary, set `McpHandlerOpts.MissingTextSummarizerLevel` (`info`, `warn`, `error` or
  `fatal`, like `MissingValidationLevel`). Each exposed method whose result lacks `JonsonMcpTextContent` is then
  reported when it is exposed. It defaults to `ignore`.

  The tool's `outputSchema` is built from the method's result type, like the `inputSchema` from the params;
  a method returning only `error` has none. Types that decode themselves (`UnmarshalJSON`) accept any value in the
  `inputSchema`, types that encode themselves (`MarshalJSON`) any value in the `outputSchema`; with `UnmarshalText`
  or `MarshalText` they are strings.
  A failed call, including a validation error, returns `isError: true` with the jonson error as text, so that
  the model can correct its arguments.
- The handler speaks MCP `2026-07-28` only (`jonson.McpProtocolVersion`): `server/discover`, `tools/list` and `tools/call`.
  Every request carries its protocol version in `_meta` and the `MCP-Protocol-Version`, `Mcp-Method` (and for
  `tools/call` `Mcp-Name`) headers; a mismatch is rejected with `400`. Older clients, which open with `initialize`,
  get an `UnsupportedProtocolVersion` error naming the supported version.
- The transport is streamable HTTP: one JSON-RPC message per `POST`, answered with `application/json`.
  There are no sessions and no server-sent events (`GET` returns 405), so any replica can answer any call.
- Requests with an `Origin` header, which browsers always send, are forbidden unless `McpHandlerOpts.AllowOrigin`
  allows the origin (protection against DNS rebinding). Clients outside a browser send no `Origin` and are served.
  To serve a browser-based client, allow its origin:

  ```go
  jonson.NewMcpHandler(methodHandler, "/mcp").WithOpts(&jonson.McpHandlerOpts{
    AllowOrigin: func(origin string, _ *http.Request) bool { return origin == "https://app.example.com" },
  })
  ```

- Tools whose method requires `*jonson.Private` are protected on `tools/call` like any other call. By default,
  `tools/list` still lists them to every caller. To only list the tools a caller may call, set
  `McpHandlerOpts.Authorizer` to a `jonson.AuthBulkAuthorizer`: it is called once per `tools/list` with all
  private methods and returns which of them the caller may call.

  ```go
  type ToolAuthorizer struct{}

  func (a *ToolAuthorizer) AuthorizedMethods(ctx *jonson.Context, methods []*jonson.RpcMeta) (map[string]bool, error) {
    allowed := map[string]bool{}
    for _, m := range methods {
      allowed[m.Method] = canCall(ctx, m.Method) // e.g. look up the caller's permissions once
    }
    return allowed, nil
  }
  ```

- The remaining `McpHandlerOpts`: `Name` and `Version` are returned as `serverInfo`, `Instructions` on
  `server/discover` tell the model how to use the tools, and `MaxBytes` limits the request body (default 5 MB).

## Hooks

Params, results and systems change how jonson treats them by implementing optional methods prefixed with
`Jonson`. All hook interfaces are declared in [`hooks.go`](hooks.go).

| Method | Implemented on | Interface | Effect |
|---|---|---|---|
| `JonsonValidate(*Validator)` | params | `ValidatedParams` | validates params before the method runs |
| `JonsonAllowUnknownFields()` | params | `AllowUnknownFieldsParams` | accepts fields the params don't declare |
| `JonsonFieldDescriptions()` | params and result structs (generated) | `FieldDescriber` | describes fields in the MCP `inputSchema` and `outputSchema` |
| `JonsonMcpTextContent()` | result | `McpTextSummarizer` | gives a short text summary of a tool result for the model |
| `JonsonMethodDescriptions()` | system (generated) | `MethodDescriber` | gives MCP tool descriptions |

## Secret

In order to encrypt/decrypt server errors that should not be exposed to the client,
`jonson.Secret` allows you to implement either your own encryption/decryption or use
the built-in one with `jonson.NewAEADSecret()`.
The AEAD secret takes the key as a **hex string** of a 32 byte key (64 hex characters, e.g. from
`openssl rand -hex 32`). In case the key is not valid hex or does not have the above mentioned length,
your program will panic.

```go
secret := jonson.NewAEADSecret(os.Getenv("JONSON_SECRET"))
```

The encrypted values end up in the `debug` field of an error's data. To read them, e.g. from a bug report,
use `secret.Decode(debug)`.

For debugging purposes, you might want to use the `jonson.NewDebugSecret()` that will
not encrypt/decrypt but simply pass the error to the rpc response.

`jonson.NewOFBSecret()` is deprecated; use `NewAEADSecret` instead.

## Putting it all together

In our main, we can now spin up our remote procedure calls:

```go
func main(){
  // in order to encrypt/decrypt our messages, we need a secret.
  secret := jonson.NewDebugSecret()

  // connect to mysql
  db := sql.MustConnect("")

  // let's initialize our providers first
  factory := jonson.NewFactory()

  // register a provider defining multiple provider instantiation methods
  factory.RegisterProvider(infrastructure.NewInfrastructureProvider(db, func() time.Time {
    return time.Now()
  }))

  // register a simple provider function
  factory.RegisterProviderFunc(infrastructure.ProvideServiceName)

  // let's instantiate our systems
  authentication := authentication.NewAuthentication()
  authorization := authorization.NewAuthorization()

  // let's expose the system's remote procedure calls to the method handler
  methodHandler := jonson.NewMethodHandler(factory, secret, nil)

  // let's register our systems with the method handler
  methodHandler.RegisterSystem(authentication)
  methodHandler.RegisterSystem(authorization)

  // right now, our systems are parsed by the method handler but not yet exposed.

  // the rpc handler will serve all remote procedure calls from the method handler
  // once calling the /rpc http endpoint
  rpcHandler := jonson.NewHttpRpcHandler(methodHandler, "/rpc")

  // the http method handler will expose all remote procedure calls
  // as their own endpoint, such as:
  // /authentication/login.v1
  // /authentication/logout.v1
  // ...
  httpHandler := jonson.NewHttpMethodHandler(methodHandler)

  // the ws handler will handle all incoming requests using websocket on the
  // http endpoint /ws
  wsHandler := jonson.NewWebsocketHandler(methodHandler, "/ws", jonson.NewWebsocketOptions())

  // the regexp handler allows us to define
  // regular expressions which will be handled
  // using the default http.Request and http.ResponseWriter wrapped by jonson's request/response structs.
  // Regexp function also allow you to pass other required parameters to the handler. Context however
  // needs to be the first argument in the handler's list of argument.
  regexpHandler := jonson.NewHttpRegexpHandler(factory, methodHandler)
  regexpHandler.RegisterRegexp(regexp.MustCompile(`^/health$`), func(ctx *jonson.Context, w *jonson.HttpResponseWriter) {
    w.Write([]byte("UP"))
  })


  // create a new server and handle all the technologies previously defined.
  server := jonson.NewServer(
    rpcHandler,
    httpHandler,
    wsHandler,
    regexpHandler,
  );

  // last step: let's listen and serve ;-)
  server.ListenAndServe(":8080")
}
```

**NOTE:** the server will ask each registered handler (rpc, ws, ...) whether they are eligible to serve
a given endpoint in the order they were passed. The first one that returns "true", wins.
In case your application is mostly used with websocket connections, it might be a good idea
to pass the wsHandler as the first argument when calling `jonson.NewServer()`.

## Exposed paths

The methods a client will try to call can be exposed with different technologies as mentioned above (websocket, http rpc, http methods or MCP).

In case you are using http methods, the paths exposed will look like this:
`/<systemName>/<methodName>.v<version>`.
The system- and method names will be converted to kebab-case: account.GetProfileV1 will result in account/get-profile.v1.
The params you send (body, query string or form, see above) need to match the json specification of your rpc's params.
The result will be returned within the body as json following your rpc's return value's json schema.

For successful remote procedure calls, the http status code will be 200.
For errors during the call, the http status code will be in the 4xx and 5xx range - depending on the
error that occured. The response body will contain the json rpc error as per [specification](https://www.jsonrpc.org/specification#error_object).

In case you are using rpc over websocket or http, your methods will look the same.
However, you will have to wrap the request in the [jsonRpc request object](https://www.jsonrpc.org/specification#request_object).

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "<systemName>/<methodName>.v<version>",
  "params": {}
}
```

The response will reflect the `id` sent in the request.
Each request should use its unique id per client to map the request to the response on the client's side.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {}
}
```

In case of an error response, the client will receive no result but an error in the response.

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32603,
    "message": "Internal error"
  }
}
```

## Graceful

Servers might want to shut down in a graceful manner, hence finishing open requests while
not accepting new incoming ones.
You can use the `GracefulProvider` which will allow you to set a custom, graceful shutdown strategy.
Furthermore, `GracefulProvider` allows you to detect server shutdowns in long-running routines
allowing you to stop those routines if applicable.

```go
logger := slog.New(...)
server := jonson.NewServer(...)
factory := jonson.NewFactory()

// instantiate a graceful provider
graceful := jonson.NewGracefulProvider().WithHttpServer(&http.Server{
  Addr: ":8080",
  Handler: server,
}).WithLogger(logger)
// or, shorter: jonson.NewGracefulProvider().WithDefaultHttpServer(server, ":8080")

// make the graceful provider known to
// long-running operations
factory.RegisterProvider(graceful)

// start the graceful server
graceful.ListenAndServe()
```

`ListenAndServe` blocks until the process receives SIGINT or SIGTERM, then shuts the server down.
By default, it waits for all open requests; `WithTimeout` limits how long it waits.

Within a long running operation and/or API endpoint, you can now check for graceful shutdowns:

```go
func (s *System) ProcessV1(ctx *jonson.Context) error {
  graceful := jonson.RequireGraceful(ctx)
  for graceful.IsUp(){
    // process long-running operation
  }
  // done processing, server is shutting down
  return nil
}
```

## Error handling

Jonson predefines a few jsonRpc default errors which are described in the spec.
You can either clone those and add your own data by calling e.g. `jonson.ErrInvalidParams.CloneWithData(yourData)`
or define your own errors by using `jonson.Error`.
A jsonRpc error consists of a message, a code and optional data.
For further details on error messages, have a look at: [jsonRpc error object](https://www.jsonrpc.org/specification#error_object)

The predefined errors, and the http status code used by the one-endpoint-per-method handler:

| Error | Code | Message | Http status |
|---|---|---|---|
| `ErrParse` | -32700 | Parse error | 400 |
| `ErrInvalidParams` | -32602 | Invalid params | 400 |
| `ErrMethodNotFound` | -32601 | Method not found | 404 |
| `ErrInternal` | -32603 | Internal error | 500 |
| `ErrServerMethodNotAllowed` | -32000 | Server error: method not allowed | 405 |
| `ErrUnauthorized` | -32001 | Not authorized | 403 |
| `ErrUnauthenticated` | -32002 | Not authenticated | 403 (not 401, which triggers basic auth in browsers) |
| `ErrTooManyRequests` | -32003 | Too many requests | 429 |
| `ErrRequestTooLarge` | -32004 | Request too large | 413 |

Errors of your own codes are returned with status 500. Any error that is not a `*jonson.Error` (e.g. from
your database) is returned as `ErrInternal`, with the original message encrypted in `data.debug` (see "Secret").

Errors carry `data.path` (the field of the params, for validation errors) and `data.details` (nested errors,
e.g. one per invalid field). To search them, e.g. in tests, use the inspector:

```go
var e *jonson.Error
if errors.As(err, &e) {
  // the first error for the field "username" with code 10000, if any
  usernameErr, _ := e.Inspect().Path("username").Code(10000).FindFirst()
  // all errors with the code of ErrInvalidParams
  all := e.Inspect().Error(jonson.ErrInvalidParams).FindAll()
}
```

`FindOne` and `FindCount(n)` additionally fail in case not exactly one (or `n`) errors match.

## Advanced factory features

In most cases, you will use the providers using their generated `RequireXXX` functions,
such as:

```go
// LoginV1 allows an account to log in
func (a *Authentication) LoginV1(ctx *jonson.Context, params *LoginV1Params) error {
  // the factory provides the database and we can now access it here in the code
  db := infra.RequireDB(ctx)
  // put your logic here
  return nil
}
```

Additionally, Jonson allows you to use any provided type in your remote procedure call's parameters.
In case the parameter is not providable and not of type `jonson.Context` or a remote procedure call `jonson.Params`,
registering the method panics at startup.

You can for example directly define the db as a parameter in your function and access it within your logic.

```go
// LoginV1 allows an account to log in
func (a *Authentication) LoginV1(ctx *jonson.Context, db *infra.DB, params *LoginV1Params) error{
  // put your login logic here
  return nil
}
```

This feature comes in very handy for guards: a provider which panics in case a precondition is not met.
Since providers are instantiated before the method runs, the method is never executed without it.
Jonson's own `jonson.Private` and `jonson.Public` work this way (see "Auth provider"); a guard of your own,
e.g. for an api key, could look like this:

```go
type ApiKeyProvider struct{}

// @generate
type ApiKey struct {
  Name string
}

func (a *ApiKeyProvider) NewApiKey(ctx *jonson.Context) *ApiKey {
  key := jonson.RequireHttpRequest(ctx).Header.Get("X-Api-Key")
  name, ok := lookupApiKey(key)
  if !ok {
    panic(jonson.ErrUnauthenticated)
  }
  return &ApiKey{Name: name}
}
```

Within your endpoint, you can now use `ApiKey` as a safeguard.
In case the caller does not send a valid api key, the provider will
panic and the method will never be executed.

```go
type StatsV1Result struct {
  Calls int `json:"calls"`
}

// StatsV1 returns the usage of the calling api key
func (a *Admin) StatsV1(ctx *jonson.Context, key *ApiKey) (*StatsV1Result, error) {
  // By now, we know that the caller sent a valid api key.
  return &StatsV1Result{
    Calls: countCalls(key.Name),
  }, nil
}
```

## Goroutines

In case you need to share a context across goroutines, you either make sure to

- instantiate _all_ necessary types beforehand (RequireXXX) or
- create a clone of your current context

The RequireA() statement could potentially call RequireB() during instantiation.
Therefore, we cannot make the Require() statement thread-safe.

In case you would have a context in two or more goroutines trying to require the same
type twice, the circular dependency checker would trigger a panic.

To avoid this issue, pass a clone of your context down to a goroutine.

```go
clone := ctx.Clone()

go func(){
  jonson.RequireLogger(clone).Info("using clone")
}()
```

## Impersonation

In certain cases, you might have to impersonate another caller: Alice needs to perform certain operation in the scope
of user Bob. Therefore, you can use the `Impersonator`. By registering `jonson.NewImpersonatorProvider()` with the
factory during initialization, you can use jonson's impersonator to make calls on behalf of other accounts.
The impersonator can impersonate multiple accounts:
In case Alice calls on behalf of Bob which calls in behalf of Charly, the Impersonator will create a new
context for all three calls; `Impersonated`, which is stored in the context, will take care to trace
all nested impersonations and make them available with a call towards `impersonated.TracedAccountUuids()`. The
impersonation of the current scope is accessible through `impersonated.AccountUuid()`.

```go
fac := jonson.NewFactory()
fac.RegisterProvider(jonson.NewImpersonatorProvider())

type DoOnUsersBehalfV1Params struct {
  jonson.Params
  OtherAccountUuid string `json:"otherAccountUuid"`
}

func (a *Authentication) DoOnUsersBehalfV1(ctx *jonson.Context, params *DoOnUsersBehalfV1Params) error {
  return jonson.RequireImpersonator(ctx).Impersonate(params.OtherAccountUuid, func(ctx *jonson.Context) error {
    // perform any logic inside the scope of OtherAccountUuid
    return nil
  })
}
```

Impersonation requires the auth provider (see "Auth provider"): before `fn` runs, the impersonator asks your
`AuthClient.IsAuthenticated` within the impersonated context. In case it returns no account, `Impersonate`
fails with `ErrUnauthorized`, so your auth client decides who may impersonate whom.
Only values marked `jonson.ShareableAcrossImpersonation` are taken into the impersonated context.

Within your `IsAuthenticated(ctx)` and `IsAuthorized(ctx)` implementations, you should access the impersonated
values which have or have not been set by a function:

```go
func IsAuthorized(ctx *jonson.Context)(*string, error){
  impersonated := jonson.RequireOptionalImpersonated(ctx)
  if impersonated != nil {
    // perform the logic for impersonated accounts
    allImpersonatedUuids := impersonated.TracedAccountUuids()
    currentImpersonatedAccount := impersonated.AccountUuid()
    return nil, nil
  }
  // perform the logic for non-impersonated accounts

  return nil, nil
}
```

## Time provider

Since it's used in basically all applications, jonson comes with a pre-defined time provider.

The time provider allows you to also mock a timing instance during your tests (see: testing).

The time provider is not registered by default. Without arguments, it provides the real time
(`jonson.RealTime`); access it with `jonson.RequireTime(ctx).Now()`:

```go
factory.RegisterProvider(jonson.NewTimeProvider())

// equivalent, explicitly passing the real time
factory.RegisterProvider(jonson.NewTimeProvider(func() jonson.Time {
  return jonson.NewRealTime()
}))
```

## Auth provider

Most applications need some sort of authentication.
You can use the jonson.AuthProvider to create an authentication provider.

`NewAuthProvider` requires you to pass an auth client which implements IsAuthenticated and IsAuthorized.

IsAuthenticated: the account is logged in;
IsAuthorized: the account is logged in _and_ has access rights to the called route.

Both return `(accountUuid, nil)` on success, `(nil, nil)` in case the caller is not authenticated/authorized
and `(nil, err)` in case the check itself failed (e.g. the database is down).
You will probably implement the client similar to the example below:

```go
type AuthClient struct {
  sessions *SessionStore
}

var _ jonson.AuthClient = (&AuthClient{})

func (a *AuthClient) IsAuthenticated(ctx *jonson.Context) (*string, error) {
  cookie, err := jonson.RequireHttpRequest(ctx).Cookie("session")
  if err != nil {
    // missing session cookie
    return nil, nil
  }
  // look up the session in your database or remote system
  accountUuid, found, err := a.sessions.AccountUuid(cookie.Value)
  if err != nil || !found {
    return nil, err
  }
  return &accountUuid, nil
}

func (a *AuthClient) IsAuthorized(ctx *jonson.Context) (*string, error) {
  accountUuid, err := a.IsAuthenticated(ctx)
  if err != nil || accountUuid == nil {
    return nil, err
  }
  // the meta tells us which method is being called
  meta := jonson.RequireRpcMeta(ctx)
  canAccess, err := a.sessions.CanAccess(*accountUuid, meta.Method)
  if err != nil || !canAccess {
    return nil, err
  }
  return accountUuid, nil
}
```

Register the provider and use `jonson.Private` and `jonson.Public` in your methods:

```go
factory.RegisterProvider(jonson.NewAuthProvider(&AuthClient{sessions: sessions}))

// GetProfileV1 can only be called by authorized accounts:
// otherwise, the method is not executed and the caller receives ErrUnauthorized
func (a *Account) GetProfileV1(ctx *jonson.Context, caller *jonson.Private) (*GetProfileV1Result, error) {
  return loadProfile(caller.AccountUuid())
}

// GetNewsV1 can be called by everyone; logged in accounts get personalized news
func (n *News) GetNewsV1(ctx *jonson.Context, caller *jonson.Public) (*GetNewsV1Result, error) {
  accountUuid, err := caller.AccountUuid(ctx) // nil in case the caller is not logged in
  if err != nil {
    return nil, err
  }
  return loadNews(accountUuid)
}
```

For nested in-process-calls of methods (e.g. method A calls method B using generated remote procedure calls),
a new context is being forked.
The new context makes sure to only copy values from context A to context B that have been explicitly marked as shareable.
Let's assume method A is private an method B is private:
caller Alice can access method A but cannot access method B;
Since method A now tries to call method B, we must make sure to _not_ provide jonson.Private to the context forked
for the call towards method B;
In case we would make private shareable, Alice (since she obtained access to method A) would implicitly gain access
to method B. This could call a potential security risk.

Public, however, can be shared between forked contexts: a logged in user will remain authenticated (logged in) across contexts.

## Testing

Jonson provides a package `github.com/doejon/jonson/jonsontest` which allows you to quickly
spin up a test context boundary. Within your test contexts, you will be able to call any API endpoint.

```go
factory := jonson.NewFactory()
factory.RegisterProvider(NewAuthenticationProvider())
secret := jonson.NewDebugSecret()
methodHandler := jonson.NewMethodHandler(factory, secret, nil)
methodHandler.RegisterSystem(NewAccount())

t.Run("gets profile", func(t *testing.T) {
  contextBoundary := jonsontest.NewContextBoundary(t, factory, methodHandler)
  var p *GetProfileV1Result
  contextBoundary.MustRun(func(ctx *jonson.Context) (err error) {
    p, err = GetProfileV1(ctx, &GetProfileV1Params{
      Uuid: testUuid,
    })
    return err
  })
  if p.Name != "Silvio" {
    t.Fatalf("expected name to equal Silvio, got: %s", p.Name)
  }
})
```

`MustRun` fails the test in case `fn` returns an error; `Run` returns the error instead, e.g. to assert
an expected error. A panic inside `fn` is turned into an error as well; to see where it happened,
pass a stack inspector (`contextBoundary.WithStackInspector(func(stack string){ t.Log(stack) })`).

The test context boundary is pre-equipped with functions to provide a http.Request and http.ResponseWriters by using `contextBoundary.WithHttpSource()`. In case needed, you can also specify your RpcMeta by using `contextBoundary.WithRpcMeta()`.

To test the validation of your params without calling a method, use `jonsontest.ValidateParams`.
It returns the validation error (or nil), which you can search with the inspector (see "Error handling"):

```go
err := jonsontest.ValidateParams(&RegisterV1Params{Username: "abc"})
if err == nil {
  t.Fatal("expected validation to fail")
}
if _, e := err.Inspect().Path("username").Code(10000).FindOne(); e != nil {
  t.Fatal("expected username to be rejected")
}
```

In case your code relies on `jonson.Graceful`, register `jonsontest.NewGracefulProvider()` instead of the
real one and call `Shutdown()` (and `Restart()`) to mimic a server shutdown.

In case you want to mock a time during testing, use `jonsontest.NewFrozenTime()` or `jonsontest.NewReferenceTime()`.
A frozen time stands still until you move it (`Add`, `AddDate`, `SetNow`, `SetTime`), a reference time starts
at the given time and then moves on like the real clock. `Sleep` really sleeps by default; replace it with
`WithSleep`, e.g. to move the mocked time forward instead of waiting:

```go
factory := jonson.NewFactory()
factory.RegisterProvider(NewAuthenticationProvider())

frozenTime := jonsontest.NewFrozenTime()

factory.RegisterProvider(jonson.NewTimeProvider(func() jonson.Time {
  return frozenTime
}))

secret := jonson.NewDebugSecret()
methodHandler := jonson.NewMethodHandler(factory, secret, nil)
methodHandler.RegisterSystem(NewAccount())

t.Run("gets profile", func(t *testing.T) {
  // do something
  frozenTime.Add(time.Second * 10)
  // do something 10 seconds later
})
```

### Testing auth

For projects relying on jonson.Private and jonson.Public for authorization and authentication, you can
use jonsontest.AuthClientMock to mock callers towards your remote procedure calls.

```go
fac := jonson.NewFactory()

// create a new auth client mock and pass the mock
// towards the auth provider
mock := jonsontest.NewAuthClientMock()
fac.RegisterProvider(jonson.NewAuthProvider(mock))

mtd := jonson.NewMethodHandler(fac, jonson.NewDebugSecret(), nil)
mtd.RegisterSystem(&System{})

// create a new account (super user in this case) which has access
// to everything
accSuperUser := mock.NewAccount("e6dd1e60-8969-4f08-a854-80a29b69d7f3").Authorized()

t.Run("accSuperUser can access set and get", func(t *testing.T) {
  // provide the super user to the context boundary - the account will now be the calling account
  // of your tests
  jonsontest.NewContextBoundary(t, fac, mtd, accSuperUser.Provide).MustRun(func(ctx *jonson.Context) error {
    // call your generated remote procedure call methods
    return GetV1(ctx)
  })
  jonsontest.NewContextBoundary(t, fac, mtd, accSuperUser.Provide).MustRun(func(ctx *jonson.Context) error {
    return SetV1(ctx)
  })
})
```

Feel free to create as many test accounts as necessary.
The test account allows you to specify the behavior of the created account:

```go
// generate an account that is neither authenticated nor authorized
acc1 := mock.NewAccount("e6dd1e60-8969-4f08-a854-80a29b69d7f3")

// generate an authenticated account (logged in)
acc2 := mock.NewAccount("e6dd1e60-8969-4f08-a854-80a29b69d7f3").Authenticated()

// generate an account that has access to everything
acc3 := mock.NewAccount("e6dd1e60-8969-4f08-a854-80a29b69d7f3").Authorized()

// generate an account that has access to specific methods only
acc4 := mock.NewAccount("e6dd1e60-8969-4f08-a854-80a29b69d7f3").Authorized(&jonsontest.RpcMethod{
  HttpMethod: jonson.RpcHttpMethodPost,
  Method:     "user/get.v1", // the method name as in RpcMeta, without leading slash
})

// allow an account to impersonate other accounts (see "Impersonation")
acc5 := mock.NewAccount("4f1b7c2e-0d6a-4c8e-9b1f-2a3d4e5f6a7b").Authorized().CanImpersonate(acc1, acc2)
```

Authorized accounts are also authenticated (logged in), so there is no need to call `Authenticated()` as well.
An account either has access to all methods (`Authorized()`) or to a list of methods; mixing both panics.

```go
//go:generate go run github.com/doejon/jonson/cmd/generate -jonson=github.com/doejon/jonson
```

By default, the generator scans the current directory; use `-path` to scan another one.

Using `go generate ./...`, you should now see three new files being created within your system:

- `jonson.procedure-calls.gen.go`: typed functions to call the system's methods in-process
- `jonson.providers.gen.go`: the `Require<Type>()` functions for types tagged with `// @generate`
- `jonson.descriptions.gen.go`: the doc comments of your methods and struct fields, used as MCP tool and
  field descriptions (see "MCP")

The procedure calls file contains all remote procedure calls specified within
the current system. These helper methods allow us to call another system's procedure without
doing an http round trip.

In order to trigger code generation, tag the types that should be requirable with `// @generate`.

Current generation limitations:
The generator currently only works with the default method name used within jonson.

## Plugins

The package `github.com/doejon/jonson/plugins` contains optional extensions.

`JsonMutatorHandler` wraps a `jonson.JsonHandler` and runs mutators on every value before it is encoded
(`WithEncodeMutator`) or after it is decoded (`WithDecodeMutator`). Pass it as
`MethodHandlerOptions.JsonHandler`.

`NilSliceNormalizer` is such an encode mutator: it turns nil slices into empty ones, so clients receive `[]`
instead of `null`. Fields tagged `omitempty` are left alone.

```go
jsonHandler := plugins.NewJsonMutatorHandler(jonson.NewDefaultJsonHandler()).
  WithEncodeMutator(plugins.NewNilSliceNormalizer())

methodHandler := jonson.NewMethodHandler(factory, secret, &jonson.MethodHandlerOptions{
  JsonHandler: jsonHandler,
})
```

To see which fields were normalized, e.g. to fix them at the source, set
`WithLogger(logger).WithLogLevel(plugins.LogLevelDebug)` on the normalizer.
